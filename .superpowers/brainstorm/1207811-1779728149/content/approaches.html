3 Approaches: Realtime Camera Management

Chọn kiến trúc phù hợp nhất với yêu cầu của bạn

A

StreamerManager Actor ★ Recommended

Tách việc quản lý streamer thành một actor riêng nhận lệnh qua channel. API endpoint ghi DB xong gửi command Start/Stop/Restart(stream_id) đến manager. Manager owns JoinSet và shutdown senders.

Pros

  • Idiomatic Tokio — không shared mutable state
  • Thay đổi có hiệu lực ngay lập tức
  • Dễ test riêng lẻ
  • Graceful shutdown từng stream

Cons

  • Phức tạp hơn — thêm channel + actor loop
  • Cần refactor inner() đáng kể
B

Periodic Reconciliation Loop

Một background task poll DB mỗi 5–10 giây, so sánh trạng thái mong muốn vs đang chạy, tự động start/stop streamer khi phát hiện thay đổi. Kiểu Kubernetes controller.

Pros

  • Đơn giản nhất — không cần channel
  • Tự heal nếu streamer crash
  • API chỉ cần ghi DB, không cần biết runtime

Cons

  • Delay 5–10s trước khi thay đổi có hiệu lực
  • Poll DB liên tục kể cả khi không có gì thay đổi
C

Direct JoinSet Manipulation

API endpoint trực tiếp spawn/abort task trong JoinSet thông qua Arc<Mutex<JoinSet>> và một map stream_id → AbortHandle được share giữa handler và server loop.

Pros

  • Thay đổi tức thì
  • Ít abstraction nhất

Cons

  • Shared mutable state — dễ race condition
  • Abort thô — không graceful shutdown
  • Khó test

Recommendation

Approach A (StreamerManager Actor) là lựa chọn tốt nhất — sạch, an toàn với async, và phù hợp với pattern của Tokio. Thêm tính năng sau này cũng dễ hơn.
